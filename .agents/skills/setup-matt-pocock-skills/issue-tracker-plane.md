# Issue tracker: Plane (+ GitHub PRs as the review surface)

Issues and PRDs for this repo live as **Plane work items**; code review happens on **GitHub PRs**. A work item is the *spec*; a PR is the *implementation + review*. Use the **Plane MCP** for work-item operations, and the `gh` CLI for pull requests. If the Plane MCP is not connected in the current session, say so and stop; do not guess an item's contents.

Fill in on setup: instance URL, workspace slug, and the project that holds this repo. Identifiers then read `<PREFIX>-42`.

Work items and PRs are independent: an item can exist with no PR (future work, a bug for another dev, a client request) and a PR with no item (a small fix). An item may be created by the ticket skills or by a person straight in the UI — both are valid; nothing here assumes an item came from an agent.

## One project per repo, not per app

Give each **repo** one project, and use **modules** for the areas inside it. Plane scopes a cycle to one project, so splitting a single repo across projects forces parallel sprints that a small team cannot plan across. Cross-cutting work also loses its home: one change touching three areas is one item in one project, or three hand-synchronised items in three.

The project boundary follows the repo and its deploy, not the directory.

## Where the spec lives

The linked work item: **description** = requirement, **sub-work-items** = acceptance criteria, **comments** = clarifications. **State** = triage status; **labels** = type; **module** = area.

## Triage states — the state machine lives in states, not labels

Map the five canonical triage roles onto Plane **states**, because that is what states are for:

| Canonical role | Plane state | State group |
| --- | --- | --- |
| `needs-triage` | **Needs triage** | Backlog |
| `needs-info` | **Needs info** | Backlog |
| `ready-for-agent` | **Ready for agent** | Unstarted |
| `ready-for-human` | **Ready for human** | Unstarted |
| `wontfix` | **Won't fix** | Cancelled |

Keep the ordinary **In progress** and **Done** states too. An item holds exactly one state, so conflicting state labels are impossible by construction. Labels stay free for type: `bug`, `task`, `debt`, `spec`, plus the `wayfinder:*` set.

## Linking a PR to its work item — optional

Opportunistic, never required — most PRs won't carry one. When a PR does implement a specific item, it can declare it with a line in the PR body:

```
Plane: <PREFIX>-42
```

Resolve the identifier in this order: (1) a `Plane:` line in the PR body; (2) any `<PREFIX>-<number>` reference in the PR body or latest commit trailer; (3) an identifier embedded in the branch name. If none resolve, that is normal — `code-review` runs its Standards axis only and does **not** treat a missing link as a finding.

## Conventions (via the Plane MCP)

- **Fetch a work item** — get by identifier, then read its description, sub-items, and comments.
- **Search** — search across the workspace by text, state, label, or module.
- **Create a work item** — create it in state **Needs triage** with a title, a structured description, and sub-items for acceptance criteria. Set the module when the area is clear.
- **Comment / state / label / module** — comment, set the triage state, apply a type label, assign the area module.

Discover the exact `mcp__plane__*` tool names at runtime; the operations above map to whatever the connected server exposes.

## When a skill says "publish to the issue tracker"

Create a Plane work item, or comment on the relevant one, via the Plane MCP. For AI-authored triage output, start the body with `> This was generated by AI.` Items a person creates by hand (e.g. from a client message) are ordinary items and need no disclaimer.

## When a skill says "fetch the relevant ticket"

Resolve the identifier (order above) and read the item via the Plane MCP — description, sub-items, and comments are the full ticket.

## PRs as a triage surface

**PRs as a request surface: no.** PRs are the review surface for internal changes, not an external feature-request queue. `code-review`'s Spec axis reviews a PR's code against its linked work item; `triage` operates on work items.

## Wayfinding operations

Used by `wayfinder`. The **map** is a single work item labelled `wayfinder:map`; **child tickets** are its **sub-work-items**, labelled `wayfinder:<type>` (`research` / `prototype` / `grilling` / `task`), assigned to the driving dev once claimed. **Blocking**: Plane's native **"Blocked by"** relation; unblocked when every blocker sits in Done. **Frontier**: the map's open sub-items with no unresolved blocker and no assignee, first in map order. **Claim**: assign the item to yourself. **Resolve**: comment the answer, move to Done, append a pointer to the map's Decisions-so-far.

Confirm on setup that native relations exist on the instance's plan. If they do not, fall back to a `Blocked by: <PREFIX>-12, <PREFIX>-19` line at the top of the child's description.
