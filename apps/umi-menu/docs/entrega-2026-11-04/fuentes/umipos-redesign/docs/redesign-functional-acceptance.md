Fecha de revisión: 2 de noviembre de 2026.

El prototipo todavía no demuestra paridad funcional con UMI. Tener las entradas del menú y sus pantallas no demuestra que existan todos sus flujos. Esta matriz identifica controles, transiciones y permisos que deben conservarse antes de sustituir una superficie actual.

Las tablas conservan la auditoría inicial. Los avances posteriores y sus pruebas están en [el reporte de implementación](dashboard-parity-implementation.md) y [REHEARSAL](../src/REHEARSAL.md). Esos avances no convierten automáticamente los 132 criterios en aprobados.

La integración real ahora existe en la rama `feat/redesign-parity`, sobre staging `b3e5bf88`.
Conserva las pantallas originales del dashboard y los controladores del POS.
La evidencia actual incluye 26 escenarios de navegador, diez escenarios adicionales con la API local y 312 pruebas nativas seleccionadas.
También pasaron 362 pruebas de integración de API en una base sintética creada desde el esquema vigente.
La [actualización de integración](staging-integration-audit.md#implementación-posterior-a-la-auditoría) enlaza los reportes del producto real.
La conexión al VPS y la copia local del 2 de noviembre reemplazan el estado anterior de acceso fallido.
Android completó vinculación y acceso con PIN mediante entrada real. La presentación parcial fue rechazada durante esa revisión visible.
La aceptación visual exige reproducir Stageshow en el cliente nativo. Las pruebas anteriores no acreditan esa correspondencia.
El recorrido operativo completo, los periféricos y los proveedores mantienen su estado pendiente hasta obtener evidencia específica.

### Cómo leer los estados

| Estado | Significado |
| --- | --- |
| **R — Representado** | Hay una pantalla, campos o datos de ejemplo. No hay un recorrido local completo que produzca el resultado esperado. |
| **L — Flujo local** | El código contiene interacción y cambio de estado local para el caso indicado. No significa que esta revisión lo haya probado en ejecución. |
| **N — No representado** | Falta el control, una transición necesaria o una variante del flujo. Una frase en `data.ts` no cuenta como interfaz. |
| **U — Integración real sin verificar** | No hay evidencia de aceptación contra el producto real, su autorización, almacenamiento, API o hardware. Aplica a **todas las filas** de esta matriz, incluso las marcadas L. |

Una fila puede tener L para el caso básico y N para un caso secundario. La prueba debe cubrir ambos. Los campos `note` de `src/dashboard/data.ts` describen requisitos, pero el render del dashboard no los muestra ni implementa sus acciones. Los formularios genéricos tampoco sustituyen una matriz de permisos o un editor de colecciones.

## Requisitos bloqueantes para staging

Las filas R/N bloquean la sustitución de su flujo actual si siguen sin resolución. Una fila L sólo habilita revisión de interacción local. Todas conservan estado U hasta la prueba real indicada. No basta con que compile la maqueta o que pase el recorrido animado.

| Gate | Requisito | Evidencia necesaria |
| --- | --- | --- |
| ST01 | Mantener las rutas, controladores, hooks y contratos reales | Diff de integración que modifica presentación y conserva propietarios de lectura/escritura. No copiar el estado de ejemplo como fuente del negocio. Comparar contra `main` y las funciones adicionales de `staging`. |
| ST02 | Resolver cada ausencia de UI antes de reemplazar esa superficie | Marcar cada ID con versión, escenario, resultado y evidencia. Si una función sigue pendiente, conservar acceso a la superficie vigente mediante una decisión explícita de integración. No declarar paridad total. |
| ST03 | Probar producto × permiso × comercio × sucursal | Casos autorizado, sólo consulta y denegado; menú, URL directa, pestaña y acción. Incluir Owner sin plataforma, plataforma sin producto y diagnóstico con un solo permiso. Verificar que el servidor mantiene la autorización. |
| ST04 | Validar dinero y recuperación | Efectivo, manual, integrado, transferencia, mixto, parcial, propina, anulación y reembolso. Reconciliar centavos, impuestos, descuentos, cambio, caja y recibos. Doble clic, reconexión y respuesta perdida no duplican operación. |
| ST05 | Validar inventario y datos de dominio | CSV/XLSX/XML reales, precisión, conversiones, costos desconocidos/cero, concurrencia de receta, importación interrumpida y recepción parcial. Comparar saldo y libros antes/después. |
| ST06 | Validar POS/KDS nativos y hardware | Ejecutar compilaciones nativas y la matriz de plataformas soportadas por el producto. Probar impresora, cajón, escáner, terminal y reconexión en hardware disponible; registrar explícitamente cualquier plataforma o periférico sin prueba. Marcos del navegador y Flutter web no prueban el POS nativo. |
| ST07 | Validar flujo completo y concurrencia | Pedido entrante o de salón → cuenta → varias rondas → KDS → entrega → cobro → recibo → turno/reportes. Dos dispositivos y cambios simultáneos; conservar identidad, permisos, canal y estado. |
| ST08 | Validar accesibilidad y tamaños sin perder acciones | Navegación por teclado, foco en diálogo, lector de pantalla básico, teléfono/tablet en ambas orientaciones y escritorio. Alcanzar las mismas operaciones; no confundir cobertura visual con prueba del sistema operativo. |
| ST09 | Ejecutar los checks del repositorio y plan de retorno | Seguir [auditoría de integración](staging-integration-audit.md) y `umi/docs/development/LOCAL_VERIFICATION_PLAYBOOK.md`.
