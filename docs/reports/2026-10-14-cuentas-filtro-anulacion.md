# Cuentas de días anteriores: revisión y anulación

Fecha: 2026-10-14. Entorno: ONCA local, una API en `127.0.0.1:4001`, base `umi_local` en `umi-bv3-pg`. POS Android final: `0.1.0+118`, contrato `2.37.0`.

## Resultado

En **Cuentas → Lista** se puede elegir **Todas las fechas** o **Días anteriores**, además del filtro existente de consumo. Una cuenta anterior puede anularse sola o seleccionarse con otras; **Seleccionar todas** toma hasta 50 por operación. La confirmación explica que hay que revisar los cobros. Si falla la operación, la selección permanece para corregir o reintentar. La lista normal sigue mostrando las cuentas actuales y el mapa no se filtra. La etiqueta de una cuenta anterior dice **Anterior**, porque puede tener más de un día.

La acción solo aparece para quien tiene `sale.lifecycle`. El servidor exige además `sale.resume.any` para cuentas de otro operador. Valida que cada cuenta sea realmente anterior al día comercial vigente, que siga abierta, que su versión coincida y que no tenga cobros que impidan anularla. La selección se procesa en una transacción: si una cuenta falla, no anula parcialmente las demás. Registra una auditoría por cuenta, libera su mesa cuando corresponde y despierta el tablero KDS. Una cuenta pagada o actual no entra por este atajo.

No activé un autocierre nocturno. [Toast](https://support.toasttab.com/en/article/Enable-Auto-Close-or-Auto-Void-for-Check-Reconciliation) documenta que, por defecto, los tickets impagos requieren intervención manual; ofrece autocierre y autoanulación configurables, y advierte que el autocierre no resuelve tickets de días previos. [Square](https://squareup.com/help/us/en/article/6594-end-of-day-reporting-with-square-for-restaurants) permite exigir la revisión de cuentas abiertas al cierre, aunque el responsable puede omitir el requisito; también admite cuentas legítimamente abiertas durante la noche. [Lightspeed](https://o-series-support.lightspeedhq.com/hc/en-us/articles/31329369881755-Finalising-your-takings) avisa de órdenes abiertas al conciliar. Mi decisión para Umi es facilitar una revisión explícita y auditable, sin convertir una venta real no cobrada en una anulación automática.

## Implementación y herramientas

- POS: `open_accounts_surface.dart`, `accounts_workspace.dart`, `catalog_surface.dart`, `sale_repository.dart` y `sale_lifecycle_controller.dart`. Se reutilizó `OpenAccountsList`; no se creó otra lista. El cliente envía identificadores y versiones de cuenta mediante el contrato tipado.
- API/contrato: ruta `POST /api/v1/pos/merchants/:merchantId/sales/carried-over/cancel`, servicio y repositorio de ventas; esquemas generados en `packages/contract`. La fuente del path es `packages/contract/src/route-table.ts`, conforme al generador del paquete. La ruta estática va antes de `:saleId`, siguiendo la precedencia explicada por [NestJS](https://docs.nestjs.com/controllers). El repositorio usa bloqueos y una transacción; el despertar de KDS usa el `NOTIFY` de PostgreSQL ya existente, documentado en [PostgreSQL](https://www.postgresql.org/docs/current/sql-notify.html). No se añadió transporte nuevo.
- Herramientas: Flutter **3.47.5**, Dart **3.13.4**, ADB **37.0.0**, pnpm **10.29.3**, Vitest **2.1.9**, tsup **8.5.1**, PostgreSQL/psql **17.10**. `apps/umi-pos/AGENTS.md` y `docs/development/LOCAL_VERIFICATION_PLAYBOOK.md` recomiendan `flutter analyze`, `flutter test`, APK profile y ADB para el POS; los scripts `test`/`generate` de `apps/umi-api/package.json` y `packages/contract/package.json` determinan Vitest y tsup. Usé `psql` por el procedimiento local de migraciones del playbook. El SQL de preparación de dos cuentas de prueba fue manual porque no se podía esperar al cambio de día durante esta verificación; sus dos identificadores estaban acotados en el `WHERE`.
- Migración reejecutable: `docs/migration/build-v3/migrations/037_cancel_suspended_carried_accounts.sql`. Permite `suspended → cancelled` en el guard de ciclo de vida. Aplicada a `umi_local` con `docker exec -i umi-bv3-pg psql -U postgres -d umi_local -v ON_ERROR_STOP=1 < docs/migration/build-v3/migrations/037_cancel_suspended_carried_accounts.sql`; repetida sin error (`CREATE FUNCTION`). No se editó un DDL numerado anterior.

## Límites comprobados y pendientes

No se probó una anulación individual contra la API real, ni la de una cuenta con pago parcial, ni la liberación de una mesa real: esos caminos tienen pruebas automatizadas/guardas, pero faltan pruebas físicas de extremo a extremo. La A9 y la A11 se verificaron por instalación y versión, no mediante clics de este flujo. La UI aproxima el día comercial con la fecha de la cuenta activa si está vigente y, si esta es antigua, con el límite local de 04:00; la API usa la zona horaria y `business_day_start` del comercio y es quien decide definitivamente. En ONCA la base confirma `America/Mazatlan` y `04:00:00`, por lo que coinciden. En comercios con otro límite, un operador podría ver una clasificación provisional distinta y recibir el rechazo seguro del servidor. El cierre de día y una política de autocierre configurable quedan fuera de este cambio.
