## PostgreSQL: plans, resource limits and isolation

**Fact:** `EXPLAIN ANALYZE` executes the statement; `TIMING OFF` suppresses per-node timer overhead while retaining total execution time. `BUFFERS` shows shared hits/reads and temp I/O. PG17 `SERIALIZE TEXT` measures output conversion but excludes network transfer. `MEMORY` describes planner memory, not total execution/JSON aggregate memory. [PG17 EXPLAIN](https://www.postgresql.org/docs/17/sql-explain.html)

**Inference — safe plan procedure:** use the API role and identical transaction-local tenant/location/device/user GUCs, a read-only transaction, bounded statement/lock timeouts, and exact request parameters. Run `EXPLAIN (ANALYZE, BUFFERS, VERBOSE, SETTINGS, FORMAT JSON, TIMING OFF)` only on the reviewed SELECT; optionally measure serialization separately. Inspect actual-vs-estimated rows, repeated subplan loops, rows removed, sort/hash spill and buffers. Never substitute worker/superuser/BYPASSRLS for API timings: RLS affects both visibility and plans. A rollback is not a universal safeguard for functions with external side effects. [RLS](https://www.postgresql.org/docs/17/ddl-rowsecurity.html), [timeouts](https://www.postgresql.org/docs/17/runtime-config-client.html)

**Fact — local source:** `sales-analysis.repository.ts` loads metadata/history minimum, products, groups and locations on every report; receipt rows contain correlated line/refund JSON, with nested refund-line aggregation. The first-sale historical MIN and catalogue reads repeat for options/current/prior requests. `period_movements` adds a refund-range EXISTS path. `LIMIT20001` bounds ticket rows, not JSON bytes, lines, refund rows, or CPU. Correlation is not automatically slow: the measured receipt query was16.1ms. **Inference:** rewrite/preaggregate only when actual loop/buffer/CPU measurements on larger inputs identify a problem; avoid row multiplication when joining multiple one-to-many relations.

**Fact — existing migration064:** receipt `(merchant_id,business_date,location_id)`; sale `(merchant_id,location_id,committed_at)`; partial committed-refund `(merchant_id,sale_id,committed_at)`. **Inference:** inspect live indexes and plans before adding duplicates. A refund business-date leading range index or refund-line join index may help a different workload, but is UNVERIFIED. B-tree leading equality/range constraints determine scan reduction; more indexes cost writes/storage. [Multicolumn indexes](https://www.postgresql.org/docs/17/indexes-multicolumn.html)

**Fact:** `work_mem` applies per sort/hash operation; concurrent operations/sessions multiply consumption. `shared_buffers` is shared cache, not the whole memory budget; PostgreSQL also relies on OS cache. **Inference:** neither variable fixes SSH startup, JS quadratic loops or oversized JSON; no global memory change is supported by the current all-hit/no-spill plan. Local compose also has a768MB DB container, making broad increases particularly unsafe. `effective_cache_size` is a planner estimate, not reserved memory. [Resource configuration](https://www.postgresql.org/docs/17/runtime-config-resource.html), [Planner costs](https://www.postgresql.org/docs/17/runtime-config-query.html)

**Fact:** `sum(bigint)` returns `numeric`; `json_agg/jsonb_agg` are not partial-mode aggregates in PG17. **Inference:** retain integer cents/exact numeric semantics, validate JS safe-integer bounds, and do not cast money to float to speed transport. `work_mem` is not an application guarantee on JSON aggregate payload size. Add explicit line/refund/response-byte and total-work bounds before expensive aggregation; an error must not silently become a financial zero or partial report. [Aggregate functions](https://www.postgresql.org/docs/17/functions-aggregate.html)

**Fact:** `pg_stat_statements` needs shared preload, query IDs and per-database extension creation; planning tracking can add overhead. It aggregates normalized queries by user/database/query ID, not merchant or HTTP route; cross-user query details require privileged access. **Fact — parent probe:** extension exists in namespace `extensions`, but `shared_preload_libraries` is empty, `track_io_timing` is off and `statement_timeout` is0. ## Pool contention and Node22 profiling

**Fact — source:** `pg.service.ts` constructs app and worker pools without overriding `max` or `connectionTimeoutMillis`; documented defaults are10 and0. `runWithMerchant` checks out a client through BEGIN, three scope-setting queries, work and COMMIT. Pool exposes total/idle/waiting counts. **Inference:** instrument acquisition separately; budget all processes/replicas against DB connections. Current measured connection count does not show contention. Combining scope settings into one parameterized SELECT can reduce round trips while preserving transaction-local RLS semantics; parallel promises on one client do not parallelize SQL. [Pool API](https://node-postgres.com/apis/pool), [pool sizing](https://node-postgres.com/guides/pool-sizing)

**Fact:** Node22 `monitorEventLoopDelay` and `eventLoopUtilization` expose loop pressure; `process.memoryUsage()` separates RSS, JS heap and external/ArrayBuffer memory. CPU profiling is built in. **Inference:** time analysis phases with `performance.now()` and profile representative larger in-memory receipts locally under Node22. Rising loop delay with fast SQL points toward synchronous JS work; RSS versus heap distinguishes JS allocations from buffers/native overhead. Sample per request cohort rather than logging every receipt. [Node22 perf_hooks](https://nodejs.org/download/release/v22.23.2/docs/api/perf_hooks.html), [process](https://nodejs.org/download/release/v22.23.2/docs/api/process.html), [CLI profiler flags](https://nodejs.org/download/release/v22.23.2/docs/api/cli.html)

**Tradeoff:** heap snapshots block the main thread and can require roughly twice the heap, potentially crashing the process. **Inference:** start with CPU timing and sampled allocation profiling; take snapshots only in a disposable/local process or approved replica with memory headroom. Raising `--max-old-space-size` does not bound total RSS or fix allocation growth. [Heap snapshots](https://nodejs.org/learn/diagnostics/memory/using-heap-snapshot), [heap profiler](https://nodejs.org/learn/diagnostics/memory/using-heap-profiler)

### Large-input bounds before new infrastructure

**Fact — source:** `purchase-baskets.ts` recomputes refund flatten/filter per receipt line; pair counting costs ∑k(k−1)/2 for basket cardinality k. The100,000 distinct-pair map cap bounds map entries, not work: many identical large baskets repeat the same pairs without growing the map. Ranking allocates an array of all pairs before sorting. Home's prior-period request currently computes basket affinity although its consumer uses comparison totals.

**Inference — narrow exact changes, ordered by cost:**

1. Index refund quantities once by line ID; preserve existing refund mode/date semantics. Process lines with iterators instead of repeated flatMap arrays where measured.
2. Avoid calculating affinity for consumers that only need totals, through an explicit projection/contract; do not redefine a full-report response or omit fields without versioning. Compare reuse benefit with separately cached full reports.
3. Bound total receipt lines/refund lines, merged visit cardinality, ∑k(k−1)/2 and distinct pairs **before** nested enumeration; check arithmetic overflow in budget accumulation. Product selection or narrower dates is an honest recovery. A repeated-basket multiplicity map can reduce enumeration to unique basket shapes exactly, but itself needs entry/byte limits and deterministic keys; add only if profiles show repetition.
4. If ranking is significant, select top100 with bounded storage while preserving current deterministic tie ordering. Counting all exact pairs still needs the bounded pair map; a top-k heap alone does not solve counting memory.
5. Report explicit range/complexity errors. Do not silently truncate baskets, sample tickets or round away cents. If product later approves approximation, return methodology/coverage in a distinct result. Worker threads or projections are later options only if bounded exact work still blocks the loop; they add transfer, cancellation and consistency costs.

These are algorithmic inferences from repository source, not benchmark claims. Test repeated-large-basket, single-huge-visit, refund-heavy, high-unique-pair and over-budget cases with exact financial reconciliation.

## Frontend first; cache invalidation choices

**Fact — source:** QueryClient uses stale15s, gc5min; sales query keys contain a serialized URL and refresh counter; equivalent parameter order can produce different strings, and0/undefined refresh slots differ. Query functions do not consume AbortSignal. Options→current/prior is a waterfall; current/prior are parallel after options. **Fact — docs:** object key property order is hashed deterministically; array order matters. Cancellation requires consuming the provided signal. [Query keys](https://tanstack.com/query/v5/docs/framework/react/guides/query-keys), [cancellation](https://tanstack.com/query/v5/docs/framework/react/guides/query-cancellation)

**Inference:** centralize normalized query options/key factories for home and detail; use a canonical object of API semantics including explicit defaults and effective visibility. Keep auth/membership/location scope in keys. Use refetch/invalidate on a stable key instead of counter-generated cache entries. Pass signal through `_apiFetch`; client cancellation does not prove server SQL/CPU stopped. Clear privileged cached data on session/scope changes. Display existing data plus a fetch indicator during background refresh rather than replacing it with a loading screen. Do not replace server operating date with the browser date to remove a legitimate dependency. Flatten only avoidable waterfalls and prefetch on meaningful navigation intent. [Defaults](https://tanstack.com/query/v5/docs/framework/react/guides/important-defaults), [waterfalls](https://tanstack.com/query/v5/docs/framework/react/guides/request-waterfalls)

**Inference — backend alternatives, simplest first:**

| Alternative                                  | Freshness/invalidation                                                                                  | Cost and limitation                                                                                                                                                                                                                                                                                             |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No financial backend cache                   | Authoritative request each time; frontend stable-key reuse15s.                                          | Recommended now. Avoids a new consistency system; optimize duplicate requests/work first.                                                                                                                                                                                                                       |
| In-flight promise coalescing                 | Share only concurrent identical authorized requests; remove settled promise.                            | No post-response staleness, but needs bounded in-flight map, per-tenant fairness, failure cleanup and careful cancellation ownership. Useful only if duplicate concurrency measured.                                                                                                                            |
| Short bounded process cache                  | TTL + explicit bypass; optionally local invalidation after successful transaction.                      | Cheap, but each replica may differ; local invalidation misses other processes/offline ingestion. Label capturedAt/cache age honestly. TTL is bounded staleness, not immediate correctness.                                                                                                                      |
| DB revision plus bounded process/Redis cache | Read an authoritative tenant/domain revision; increment transactionally with writes, include it in key. | Stronger cross-process invalidation but requires all writers and migrations; a cache fill must use a snapshot coherent with revision to avoid labeling old data with new revision. Old keys need TTL/eviction. A single merchant revision is simple but invalidates broadly and may contend at high write rate. |
| Durable post-commit outbox + revision/TTL    | Consumer invalidates/advances revisions after commit; replay handles outages.                           | More moving parts and propagation lag; useful if an existing authoritative event/outbox covers every writer. Do not invent such coverage. Redis Pub/Sub alone loses events while disconnected.                                                                                                                  |
| Materialized/projection tables               | Explicit ingest/rebuild/versioning, reconciled to canonical receipts/refunds.                           | Highest adoption cost; no present timing evidence warrants this.                                                                                                                                                                                                                                                |

**Inference — authorization and scope:** execute current permission/membership/effective-location checks **before every cache lookup**, even on a hit. Key report/schema version, merchant, effective visibility (including all-branches versus a branch), relevant user/permission identity or authorization revision, timezone/business cutoff/currency, canonical date/filter/refund/basket/group parameters and applicable sales/refund/catalogue/group revisions. Do not include JWT secrets. Never share cached rows merely because merchant IDs match; API RLS visibility must remain equivalent. Current source `sales-analysis.service.ts` has permission checks before repository reads; preserve that invariant.

**Inference — invalidation coverage:** finalized sales, committed refunds/voids/corrections, delayed/offline ingestion, product/category reassignment/color/name and analysis-group changes, timezone/cutoff/currency configuration, and authorization changes. Refunds can change an older `sale_result` period, so historical dates are not inherently immutable. Catalogue categories are current by contract, so even old date reports can change after reassignment. Service-level invalidation inside a DB callback happens before COMMIT and is incorrect if the transaction rolls back. A revision increment in the same transaction or an outbox record committed with the write avoids that race. Locate every actual writer (`pos-checkout.repository.ts`, `pos-exception.repository.ts`, dashboard catalogue/groups and ingestion paths) before claiming complete coverage.

**Inference — bounded storage contract:** cap entries, accounted bytes, tenant share, in-flight requests and maximum accepted payload; TTL every result, never cache errors/authorization failures, and clean up on all settle paths. Limit refresh stampedes without allowing one cancelled caller to cancel every coalesced caller. A forced refresh must bypass/invalidate backend cache, not only change a frontend key. Preserve original report `capturedAt` on a hit.

**Tradeoff:** Redis maxmemory policies and replication/AOF buffers affect capacity; local Redis is configured `noeviction`, so adding large report blobs can instead reject writes. Changing shared Redis to global eviction risks queue/session keys. **Inference:** if Redis eventually wins a measured comparison, use separately bounded cache resources and appropriate policy; a key prefix or logical DB alone does not reserve memory. Gracefully fall back to the authoritative read if cache unavailable. [Eviction](https://redis.io/docs/latest/develop/reference/eviction/), [notifications are fire-and-forget](https://redis.io/docs/latest/develop/pubsub/keyspace-notifications/)
