# Umi Support — investigación Android 11

Fecha: 2026-10-27. Alcance: app local autorizada por el propietario; reconocer el diálogo de depuración Wi-Fi para SSID `UmiPOS` y BSSID `bc:07:1d:ca:ae:61`, marcar Always allow y pulsar Allow. Investigación solamente: no compilación, instalación, comandos al dispositivo ni cambios al repositorio.

## Resultado y límite principal

**HECHO:** AOSP `WifiDebuggingActivity` hereda de `AlertActivity`. Esta última sobrescribe `dispatchPopulateAccessibilityEvent()` y publica la clase `android.app.Dialog`. Por eso `AccessibilityEvent.className` NO permite comprobar que la Activity sea exactamente `com.android.systemui.wifi.WifiDebuggingActivity`. El nombre de la clase del nodo raíz tampoco es el componente Activity. [AlertActivity, Android 11 r48, líneas 70–83](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-11.0.0_r48/core/java/com/android/internal/app/AlertActivity.java).

**RECOMENDACIÓN / INFERENCIA:** reconocer la firma estructural y textual del diálogo AOSP emitido por el SystemUI auténtico: paquete exacto, firma de plataforma, root activo, IDs y textos completos derivados de recursos locales. Esta estrategia identifica el diálogo esperado; **no autentica el nombre exacto de la Activity**. No presentar ese requisito original como cumplido. Tampoco usar `ActivityManager.getRunningTasks()`: la API limita la información disponible a apps de terceros desde Android 5. [ActivityManager](<https://developer.android.com/reference/android/app/ActivityManager#getRunningTasks(int)>).

## Verificador recomendado

Las siguientes son decisiones de diseño, no garantías del framework:

1. Verificar que `com.android.systemui` existe y coincide con el firmante de `android` mediante PackageManager. Rechazar errores o falta de coincidencia. `FLAG_SYSTEM`/`FLAG_UPDATED_SYSTEM_APP` pueden ser comprobaciones adicionales, pero Android advierte que `FLAG_SYSTEM` solo no basta para decisiones de seguridad. La coincidencia en iMin está **UNVERIFIED**. [ApplicationInfo](https://developer.android.com/reference/android/content/pm/ApplicationInfo#FLAG_SYSTEM).
2. Obtener recursos del SystemUI instalado y resolver los cuatro nombres `wifi_debugging_*`. Si falta un recurso, cambia la configuración durante el intento o falla su lectura/formato: no actuar. Usar las cadenas de esa configuración, sin traducciones codificadas ni un fallback permisivo. `Resources.getIdentifier()` es API pública y devuelve 0 al no encontrar el nombre. Los nombres internos de SystemUI no son un contrato SDK estable. [Resources](<https://developer.android.com/reference/android/content/res/Resources#getIdentifier(java.lang.String,%20java.lang.String,%20java.lang.String)>).
3. Consultar `getRootInActiveWindow()`. Exigir root y nodos del paquete exacto `com.android.systemui`, una sola coincidencia por ID esperado y misma `windowId`. Comparar título, texto de casilla y botón completos; casilla checkable y controles visibles/habilitados. `flagReportViewIds` es necesario para recibir IDs de recurso completos. [AccessibilityServiceInfo](https://developer.android.com/reference/android/accessibilityservice/AccessibilityServiceInfo#FLAG_REPORT_VIEW_IDS).
4. Generar un conjunto finito de mensajes esperados con el recurso local: SSID `UmiPOS` o `"UmiPOS"`, y el BSSID fijo en mayúsculas o minúsculas. Comparar el mensaje entero. No aceptar otro SSID, otro BSSID, espacios añadidos, prefijos/sufijos ni coincidencias parciales. La variante sin comillas es compatibilidad propuesta para OEM; su necesidad real en iMin está **UNVERIFIED**.
5. Si la casilla está desmarcada, pulsar solo ese nodo mediante `ACTION_CLICK`. Después volver a obtener root y repetir todos los requisitos, incluida la misma ventana y la casilla ya marcada. Solo entonces pulsar `button1`. Si la casilla ya estaba marcada, no alternarla. Un `performAction()` exitoso no demuestra por sí solo que se persistió la autorización. [AccessibilityNodeInfo: búsqueda por ID, refresh y performAction](https://developer.android.com/reference/android/view/accessibility/AccessibilityNodeInfo).
6. Reintentos breves y acotados para renderizado/conexión; cancelar cuando cambia la ventana, el paquete, el mensaje, la configuración o la conexión del servicio. Nunca sustituir un fallo por coordenadas, gestos globales o búsqueda genérica de texto.

**LÍMITE:** root fresco, `refresh()` y revalidación reducen lecturas obsoletas; la secuencia consulta/acción no es una transacción atómica. Las API de accesibilidad permiten cambios del árbol en cualquier momento. No afirmar una garantía absoluta frente a cambios simultáneos. [AccessibilityService, recuperación de contenido](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService).

## Reconexión, diálogo ya abierto y reinicio

**HECHO:** AOSP registra la conexión de accesibilidad antes de llamar `onServiceConnected()`. `getRootInActiveWindow()` utiliza esa conexión; no requiere haber recibido un evento de apertura ni una clase de evento particular. [AccessibilityService.java, DO_INIT y getRootInActiveWindow](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-11.0.0_r48/core/java/android/accessibilityservice/AccessibilityService.java).

**INFERENCIA / RECOMENDACIÓN:** invocar el mismo verificador desde `onServiceConnected()` y desde eventos pertinentes permite recuperar un diálogo ya abierto, si sigue siendo la ventana activa y expone el árbol esperado. Si el root inicialmente es null, efectuar unos pocos reintentos programados; no darlo por reconocido sin verificar. Esta decisión no necesita `flagRetrieveInteractiveWindows` si solo utiliza el root activo y sus windowIds. Sin esa bandera, `getWindows()` está vacío y `node.getWindow()` devuelve null: no añadir requisitos basados en esos métodos accidentalmente. [AccessibilityServiceInfo](https://developer.android.com/reference/android/accessibilityservice/AccessibilityServiceInfo#FLAG_RETRIEVE_INTERACTIVE_WINDOWS).

**HECHO:** el sistema administra el servicio habilitado por el usuario. AOSP lo enlaza con `BIND_AUTO_CREATE`; Android 11 distingue también servicios desconectados/crashed. No existe garantía documentada de recuperación inmediata tras todos los fallos u OEM. Un force-stop del paquete elimina su componente de la lista habilitada en AOSP: un boot receiver o `START_STICKY` no deben presentarse como solución para habilitarlo otra vez. [AccessibilityServiceConnection](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-11.0.0_r48/services/accessibility/java/com/android/server/accessibility/AccessibilityServiceConnection.java), [AccessibilityUserState](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-11.0.0_r48/services/accessibility/java/com/android/server/accessibility/AccessibilityUserState.java), [AccessibilityManagerService, onHandleForceStop](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-11.0.0_r48/services/accessibility/java/com/android/server/accessibility/AccessibilityManagerService.java).

**HECHO:** `android:directBootAware="true"` permite ejecutar el componente antes del primer desbloqueo; la configuración necesaria debe estar embebida o en device-protected storage. AOSP omite servicios no direct-boot-aware antes del desbloqueo y enlaza los habilitados que sí lo son. No hace falta que Umi Support arranque manualmente su AccessibilityService desde `BOOT_COMPLETED`. [Direct Boot](https://developer.android.com/privacy-and-security/direct-boot), [AccessibilityManagerService, updateServicesLocked líneas 1483–1514](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-11.0.0_r48/services/accessibility/java/com/android/server/accessibility/AccessibilityManagerService.java).

**UNVERIFIED en iMin:** persistencia del ajuste tras reboot, enlace antes/después de unlock, visibilidad del diálogo con pantalla bloqueada, política de ahorro/gestión OEM, accesibilidad de sus controles y aceptación real de `ACTION_CLICK`. Ser direct-boot-aware no asegura que Wi-Fi/KeepADB, el diálogo y todos los recursos estén disponibles antes del desbloqueo. La documentación oficial iMin confirma un flujo de diálogo de autorización inalámbrica, pero no documenta sus IDs ni el ciclo de vida del servicio de accesibilidad. [iMin Docking Debugging v1.8](https://oss-sg.imin.sg/docs/en/DockingDebugging.html).

## Permisos y alcance mínimo

- Declarar el servicio protegido por `android:permission="android.permission.BIND_ACCESSIBILITY_SERVICE"`, su intent-filter y metadata; declarar `canRetrieveWindowContent=true`, `flagReportViewIds`, paquete `com.android.systemui` y tipos de eventos necesarios. `BIND_ACCESSIBILITY_SERVICE` protege la entrada del servicio para que solo Android pueda enlazarlo; no es un permiso privilegiado que la app deba obtener para pulsar controles. Activación inicial manual del propietario en Ajustes. [Declaración y ciclo de vida](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService), [permiso](https://developer.android.com/reference/android/Manifest.permission#BIND_ACCESSIBILITY_SERVICE).
- No se necesita consultar Wi-Fi para validar el texto del diálogo. No proponer permisos de red, ubicación, cambios Wi-Fi, root, `WRITE_SECURE_SETTINGS`, ADB ni lógica de puertos/endpoints. KeepADB permanece fuera de esta función. Un receiver de arranque y `RECEIVE_BOOT_COMPLETED` son innecesarios para el enlace del servicio.
- La lectura de información/recursos de SystemUI puede requerir visibilidad de paquete al apuntar a API 30; un `<queries>` específico para `com.android.systemui` es una opción acotada. Comportamiento exacto del firmware: **UNVERIFIED**.
- Alternativa pública para conocer nombres de Activity: UsageEvents con acceso de uso adicional. No se recomienda aquí: amplía acceso y desde Android 11 `queryEvents()` devuelve null antes del primer desbloqueo. [UsageStatsManager](<https://developer.android.com/reference/android/app/usage/UsageStatsManager#queryEvents(long,%20long)>), [UsageEvents.Event](https://developer.android.com/reference/android/app/usage/UsageEvents.Event#ACTIVITY_RESUMED).

## Pruebas propuestas sin autorizar redes extra

**Offline, con snapshots/dobles sintéticos:** éxito con el único par autorizado; SSID similar, BSSID distinto, BSSID añadido como sufijo, mensaje cambiado, paquete falso, firma errónea, recursos faltantes, IDs ausentes/duplicados, root null/obsoleto, ventana distinta entre ambas acciones, casilla ya marcada, clic fallido y eventos repetidos. Exigir cero acciones para cualquier caso no reconocido y nunca pulsar Allow si no se confirmó casilla marcada. No simular estas negativas conectando el POS a redes adicionales.

**Canario físico en la red autorizada:** primero inspección sin acciones de paquete/firma/recursos/IDs/textos. Después verificar un único flujo real del par permitido, reapertura del diálogo cuando corresponda, conexión del servicio con diálogo ya presente, reboot y reconexión, pantalla apagada y desbloqueo. Si Always allow ya suprime futuras aperturas, registrar ese resultado y no borrar confianza ni cambiar de red para forzar otra prueba. Estas verificaciones de dispositivo siguen **UNVERIFIED**; no se ejecutaron en esta investigación.
