# Promotions — the rule engine, the till tab, and the console screen

- **Date:** 2026-10-12
- **Status:** design. Not implemented.
- **Author:** design session, at the owner's request: "necesitamos añadir una pestaña de promos y en el
  dashboard un lugar donde crearla".
- **Labels:** `FACT` comes from this repository. `INFERENCE` is my reasoning. `USER-PRIMARY` comes from
  the owner's words. `MARKET` comes from a vendor source named in the text.

---

## 1. The problem

A café owner wants to run an offer: "2 for 1 on cappuccinos", "15% off the whole bill on Monday", "the
dessert is free with a main". Today the product can only do one thing: a cashier types a discount by
hand at the till. `FACT` — `DiscountDraft` in `packages/contract/src/pos-checkout.ts` carries a type
(line or order, percentage or fixed), a value and a reason. A manager approves it.

Two people need this feature.

- **The owner** creates the offer once, in the console, and stops it later. The owner does not want to
  explain the offer to every cashier.
- **The barista** applies the offer in three seconds at the till, during a rush. The barista must see
  which offers are live and why an offer does not apply.

## 2. The model

**A promotion is a RULE. The result of the rule is a DISCOUNT FACT.**

This split is not new. The repository already made it. `FACT` —
`docs/migration/build-v3/20_merchant.sql:1388` creates `merchant.order_discount` with
`kind in ('discount','comp','promo')`, a `code` ("mirrors DiscountPreview.entries[].code"), a `label`
("what the receipt prints") and an `amount` that is always positive. The comment on that table states
the boundary: _"Applied discount FACTS (incl. comps as the 100%-off case). The promo RULE engine is
still deferred; this is what a receipt prints and what a total subtracts."_

So this design builds the deferred half. The rule engine produces the facts that the rest of the
product already reads.

| Object           | What it is                                                                     | Where it lives                        |
| ---------------- | ------------------------------------------------------------------------------ | ------------------------------------- |
| Promotion        | A rule the owner writes: name, code, scope, value, schedule, locations, state. | New table `merchant.promotion`.       |
| Discount fact    | Money removed from one line or from the order.                                 | `merchant.order_discount`, unchanged. |
| Discount policy  | What the merchant allows (limits, approval, permissions).                      | `DiscountPolicy`, unchanged.          |
| Discount preview | The money math, before the sale commits.                                       | The checkout preview, unchanged.      |

**The source of truth is the API.** The till holds a read-only cache of the live promotions for its
location. The till does not calculate the money. `INFERENCE` — the checkout already computes every
total on the server, and a second engine in the client would disagree with it.

### What happens to a promotion in the hard cases

- **A refund, whole or partial.** The promotion does not re-evaluate. The discount is a fact on the
  order, and the existing refund allocation divides it across the returned lines. `FACT` —
  `DiscountRefundAllocation` and `RefundAllocation` in the contract.
- **A cancelled line, before the commit.** The draft goes away with the line. No fact exists.
- **A cancelled line, after the commit.** This is a return. The refund path handles it.
- **A re-opened sale.** A committed sale never re-opens. A suspended sale keeps its lines and its
  discounts. A promotion applies only while the cart is a cart.
- **A promotion that stops.** Applied facts stay. The rule stops for new carts.

## 3. The kinds of promotion

### In the first version

1. **Order value off.** A percentage or a fixed amount off the whole bill.
2. **Line value off.** A percentage off a set of products or categories.

Both kinds carry: a start time and an end time, a set of locations, and a state
(`draft` → `active` → `stopped`).

### Deliberately out of the first version

- **Buy N get one free.** `INFERENCE` — the cheap line is free, and the money must be exact. The
  allocation needs a rule for the cheapest item, and the rule must survive a partial refund. This is
  a second piece of money math, and it deserves its own slice.
- **A coupon the customer types.** It needs a code path in the customer's hands. The cashier path
  proves the money first.
- **Two promotions on one line.** Stacking needs an order of precedence. The first version forbids it.
- **Automatic application.** See the open questions. The first version applies a promotion when the
  cashier asks for it.

## 4. The surfaces

### The till tab

A new entry in the rail, **Promos**, between Ventas and Mesas. `INFERENCE` — the rail already groups
the work by place: the menu, the drawer, the sales, the tables, the kitchen, the orders. An offer is
a sales action, so it sits next to Ventas.

The tab shows:

- the live promotions for this location, with the name and the value ("15% en todo", "2x1 capuchino");
- for each promotion, if it applies to the current cart, and if not, the reason in the operator's
  words ("falta un capuchino", "fuera del horario");
- one action per promotion: **Aplicar**. The tab shows the discount that the API previewed.

The tab does not let the operator create or change a promotion. That is owner work.

### The console screen

A new screen in the dashboard, under the same area as hours and categories. The screen lists the
promotions of the merchant and lets the owner:

- create a promotion: a name, a code, the kind, the scope, the value, the dates, the locations;
- see its state, and stop it;
- read what it removed from the sales in a period. `INFERENCE` — the owner will ask "did this offer
  pay for itself?" in the first week.

### The paper

The receipt already has a discount row. `FACT` — `discountMinorUnits` in the receipt print payload and
in `ReceiptPrintPayload`. The promotion adds its **name** to that row, from the `label` column.
`FACT` — the comment on `merchant.order_discount` says the label is what the receipt prints.

The receipt prints one row for each applied fact, for example: `2x1 capuchino   −MXN 45.00`.

## 5. The API

### Till routes

| Route                                                            | Purpose                                                                                          | Permission            |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | --------------------- |
| `GET /pos/merchants/:m/promotions?locationId=`                   | The live promotions for this location. The till caches the answer.                               | `cart.read`           |
| `POST /pos/merchants/:m/carts/:cartId/promotions`                | Apply one promotion to the open cart. The body carries the promotion id and the idempotency key. | `cart.discount.apply` |
| `DELETE /pos/merchants/:m/carts/:cartId/promotions/:promotionId` | Remove an applied promotion from the cart.                                                       | `cart.discount.apply` |

`FACT` — the apply permission follows the policy object, which already names a
`requiredPermission` and an `approvalPermission` for discounts
(`packages/contract/src/pos-checkout.ts`). The promotion reuses that permission. A promotion whose
value passes the cashier threshold needs the same approval as a manual discount.

### Console routes

| Route                                        | Purpose                   | Permission        |
| -------------------------------------------- | ------------------------- | ----------------- |
| `GET /api/merchants/:m/promotions`           | List.                     | `merchant.manage` |
| `POST /api/merchants/:m/promotions`          | Create.                   | `merchant.manage` |
| `PATCH /api/merchants/:m/promotions/:id`     | Change a draft.           | `merchant.manage` |
| `POST /api/merchants/:m/promotions/:id/stop` | Stop an active promotion. | `merchant.manage` |

The promote-to-active path is an administrative command, in the same shape as the other owner actions
in `docs/architecture-transition/PROJECT_CANONICAL_STATE.md`: it writes an audit event and it carries a
fingerprint.

## 6. The money rules

1. **The value is an integer in minor units or in basis points.** `FACT` — `DiscountDraft` uses
   `basisPoints` (1..10000) or a fixed `Money`. The promotion writes the same two fields.
2. **The API computes the discount.** The till sends the promotion id. The API evaluates the rule
   against the cart and returns the preview. `INFERENCE` — one engine, one answer.
3. **Prices include tax.** The discount lowers the total after tax. The promotion never computes tax
   on its own. `FACT` — `taxIncludedLabel` and the checkout totals.
4. **One discount per line.** A second promotion, or a manual discount on the same line, is refused
   with a named code. `INFERENCE` — stacking needs a precedence rule that does not exist.
5. **A promotion does not touch the drawer.** It changes the sale total, not the cash ledger. The
   drawer sees the cash that the customer gives. `FACT` — `cash_ledger_entry` records cash, not
   discounts.
6. **Loyalty and customer value stay separate.** A reward is a tender, not a discount. Both can apply
   to one sale, and the existing allocation adds them. `INFERENCE`
7. **The cash-up shows the discount.** The reports already carry `discountMinorUnits`
   (`packages/contract/src/reports.ts`). The promotion adds a dimension to that number: the promotion
   code. `FACT`

## 7. Offline

This till sells offline. `FACT` — `apps/umi-pos/lib/features/offline` and the offline journal.

**The first version refuses to apply a promotion while the till is offline.** The reason is exact: the
rule needs the server to evaluate it, and the discount changes the money that the customer pays.
`INFERENCE` — an offline promotion would need a frozen rule set, a version, and a replay rule. That is
a slice of its own.

An offline sale still works. The cashier charges the full price, and the till records the sale. The
promotion tab shows the promotion as **no disponible sin conexión**.

Slice 3 can add one safe case: a fixed-amount order promotion with no schedule. That rule needs no
evaluation against products and no clock.

## 8. The first slice

The smallest thing a café can use on day one:

1. The owner creates an **order value off** promotion: a name, a code, a percentage or a fixed
   amount, a start date and an end date, and one or more locations.
2. The till shows the promotion in the Promos tab while it is live.
3. The cashier applies it to the cart. The API previews the discount. The cashier confirms.
4. The receipt prints the promotion name and the amount.
5. The console lists the promotion and stops it.

Then, in order:

1. **Slice 2:** line value off, with a scope of products and categories.
2. **Slice 3:** the offline rule for a fixed order amount.
3. **Slice 4:** buy N get one free.
4. **Slice 5:** automatic application, and the promotion report.

## 9. Open questions for the owner

1. **Does a promotion apply by itself, or does the cashier apply it?**
   _My choice for the first version: the cashier applies it._ Reason: the money must be auditable
   from the first day, and an automatic rule that nobody sees is hard to correct at the counter.
   Automatic application is slice 5.
2. **Can a promotion combine with a manual discount?**
   _My choice: no._ One discount per line. The API refuses the second one with a named code. Reason:
   two discounts on one line need a precedence rule, and the price of a mistake is a refund.
3. **Does the promotion follow a line when the table splits or merges?**
   _My choice: yes._ The discount belongs to the line. A split keeps the discount on its line. Reason:
   the money already moved with that line.
